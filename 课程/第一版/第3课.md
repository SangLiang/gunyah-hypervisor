# 第 3 课 · L1 启动链第三段：`boot_cpu_cold_init` / `boot_cpu_warm_init` —— 每 CPU 本地结构是怎么搭起来的

按学习地图：上一课跟完了 `boot_cold_init` 上的 `partition` / `memdb` / `idle`；今天往下走两步，打开 `boot_cpu_cold_init` 和 `boot_cpu_warm_init` 这两条事件链，看**每个 CPU 自己的本地结构**是怎么搭起来的，以及为什么 `boot.c` 里 `boot_cpu_cold_init` 之后才出现第一句 `TRACE_AND_LOG`。

> 本课目标：能用一句话讲清 **cold（建骨架）** 和 **warm（通电）** 的区别；能说清 `cpulocal` 为什么是 `first`、`power` 为什么也是 `first`；并理解 preempt 的"启动锁"是怎么把整条启动链锁住的。

## 0. 先对齐：上一课的事件链 + 本课定位

`hyp/core/boot/src/boot.c` 的 `boot_cold_init()`（Boot CPU 冷启动）：

```c
trigger_boot_cpu_early_init_event();    // ← 本课第 1 节：preempt 启动锁
trigger_boot_cold_init_event(cpu);      // 上一课主战场（partition/memdb/...）
trigger_boot_cpu_cold_init_event(cpu);  // ← 本课第 2 节：建 per-CPU 骨架
// 此后可 log
TRACE_AND_LOG(... "Hypervisor cold boot" ...);
trigger_boot_cpu_warm_init_event();     // ← 本课第 3 节：通电（重新初始化硬件）
trigger_boot_hypervisor_start_event();  // 下一课
trigger_boot_cpu_start_event();         // ← 本课第 6 节：preempt 解锁
thread_boot_set_idle();                 // 不再返回
```

### 0.1 三条入口，谁跑哪条链

同一个 `boot.c` 里有**三个**入口函数，对应 CPU 的三种上电场景。它们跑的事件链不一样：

| 入口函数 | 场景 | 跑的事件链 |
|----------|------|-----------|
| `boot_cold_init(cpu)` | Boot CPU 第一次上电 | early → cold_init → **cpu_cold_init** → **cpu_warm_init** → hypervisor_start → cpu_start |
| `boot_secondary_init(cpu)` | 其他 CPU 第一次上电 | early → **cpu_cold_init** → **cpu_warm_init** → cpu_start |
| `boot_warm_init()` | 任意 CPU 从休眠/热插拔回来 | early → **cpu_warm_init** → cpu_start |

读法：
- `boot_cold_init`（全局）和 `boot_hypervisor_start`（高层服务）**只在 Boot CPU 跑一次**，所以 `boot_secondary_init` 和 `boot_warm_init` 都没有它们。
- `boot_cpu_cold_init` **只在冷启动跑**（Boot CPU 和其他 CPU 第一次上电都跑；热启动不跑）。
- `boot_cpu_warm_init` **每次上电都跑**（冷启动会跑一遍，热启动也跑）。

### 0.2 一句话区分 cold 和 warm

记住一个口诀：

> **`boot_cpu_cold_init` = 建骨架（软件层的 per-CPU 数据结构，只建一次）；`boot_cpu_warm_init` = 通电（重新初始化硬件寄存器，每次上电都做一遍）。**

类比：cold 是盖房子（打地基、砌墙），warm 是搬进去住之前先通水通电。盖房子只盖一次；但每次出远门回来，水电气都得重新开一遍。所以：
- **冷启动 = 盖房子 + 通电**（`cpu_cold_init` 跑完，紧接着 `cpu_warm_init` 也跑一遍）。
- **热启动 = 只通电**（房子还在，只需重新开硬件寄存器）。

这就是为什么 `boot_cpu_cold_init` 上的 handler 多在初始化 `CPULOCAL_*` 数组、分配 per-CPU 对象；而 `boot_cpu_warm_init` 上的 handler 多在写系统寄存器、enable 本地 IRQ。

下面这张图把三条入口和它们各自跑的事件链**按同一事件对齐**画出来，帮助区分 cold/warm 的边界（空虚线框 = 这条入口不跑该阶段）：

![三条入口与事件链](图/第3课-三条入口.svg)

读法：横向是时间。注意 `cpu_cold_init` 只出现在前两行（冷启动），`cpu_warm_init` 三行都有——这就是"建骨架只建一次，通电每次都做"的体现。

## 1. `boot_cpu_early_init`：preempt 的"启动锁"

在进入 `cpu_cold_init` / `cpu_warm_init` 之前，三条入口的**第一句**都是 `trigger_boot_cpu_early_init_event()`。这条事件链上目前只有一个订阅者：`preempt`。

`hyp/core/preempt/preempt.ev`：

```text
subscribe boot_cpu_early_init
	acquire_preempt_disabled

subscribe boot_cpu_start
	priority last
	release_preempt_disabled
```

注意 `acquire_preempt_disabled` / `release_preempt_disabled`——这不是普通的 handler，而是**锁的获取/释放标记**。它告诉代码生成器：这条订阅要配对地拿/放 `preempt_disabled` 这把"锁"。

### 1.1 preempt_disable_count 的位布局

`hyp/core/preempt/preempt.tc`：

```text
define preempt_bits enumeration {
	count_max = 15;
	cpu_init;
	in_interrupt;
	abort_kernel;
};
```

`hyp/core/preempt/src/preempt.c`：

```c
static _Thread_local count_t preempt_disable_count;

static const count_t preempt_count_mask =
	(count_t)util_bit((index_t)PREEMPT_BITS_COUNT_MAX + 1U) - 1U;
static const count_t preempt_cpu_init    = util_bit(PREEMPT_BITS_CPU_INIT);
static const count_t preempt_in_interrupt = util_bit(PREEMPT_BITS_IN_INTERRUPT);
static const count_t preempt_abort_kernel = util_bit(PREEMPT_BITS_ABORT_KERNEL);
```

`preempt_disable_count` 是一个 `_Thread_local` 计数器，但它**不止是计数**——它把好几个独立的"标志位"挤进同一个字里：

![preempt_disable_count 位布局](图/第3课-preempt位布局.svg)

- **低 16 位（count，bit 0–15）**：普通的 `preempt_disable()` / `preempt_enable()` 嵌套计数。每次 `preempt_disable()` 加 1，`preempt_enable()` 减 1；减到 0 才真正开抢占。`count_max = 15` 表示计数场的最高位是 bit 15，不是“只能数到 15”。
- **cpu_init 位（bit 16）**：启动锁。`boot_cpu_early_init` 时置 1，`boot_cpu_start` 时清 0。
- **in_interrupt 位**：进中断处理时临时置 1。
- **abort_kernel 位**：abort 处理时置 1。

### 1.2 启动锁干了什么

```c
void
preempt_handle_boot_cpu_early_init(void) LOCK_IMPL
{
	// Prevent an accidental preempt-enable during the boot sequence.
	preempt_disable_count |= preempt_cpu_init;
}

void
preempt_handle_boot_cpu_start(void) LOCK_IMPL
{
	// Boot has finished; allow preemption to be enabled.
	assert((preempt_disable_count & preempt_cpu_init) != 0U);
	preempt_disable_count &= ~preempt_cpu_init;
}
```

逐段拆解：

1. **`preempt_handle_boot_cpu_early_init`**：在 `preempt_disable_count` 上**或**上 `preempt_cpu_init` 位。注意是 `|=`，不是 `=`——不会破坏低位的 count。这一位置上之后，即使后面有人调 `preempt_enable()` 把 count 减到 0，整个 `preempt_disable_count` 仍然非 0，调度器不会切走当前线程。
2. **`preempt_handle_boot_cpu_start`**（在 `boot_cpu_start` 上，`priority last`，即最后一步）：把 `cpu_init` 位清掉。注释说"Boot has finished; allow preemption to be enabled"。从这一刻起，`preempt_enable()` 才真正可能把 count 减到 0 并开中断。

要点：
- `cpu_init` 位是一把**启动期总锁**：从 `boot_cpu_early_init`（链头）一直锁到 `boot_cpu_start`（链尾）。整条启动链都被它锁住。
- 这把锁防的是"启动期间有人意外开抢占"。启动期间很多数据结构还没建好，一旦被抢占切走，可能跑到一个半成品上下文里。
- `boot_cpu_start` 是 `priority last`，确保它是 `boot_cpu_start` 事件链上**最后一个** handler——前面所有 handler 都跑完，才解锁。

> 类比：`cpu_init` 位是工地施工期间的"总闸"。施工期间（early → start）总闸拉下，谁都不许通电（开抢占）；施工结束（`boot_cpu_start` 最后一步）总闸推上，之后才能正常用电。即使某个工种提前完工想通电（`preempt_enable` 把 count 减到 0），总闸不开也通不上。

### 1.3 为什么用"位"而不是单独一个变量

把 `cpu_init` / `in_interrupt` / `abort_kernel` 塞进同一个 `count_t`，而不是用三个独立 bool，好处是：**判断"能否抢占"只需要看一个字是否非 0**。`assert_preempt_disabled()` 就是 `assert(preempt_disable_count != 0U)`——不管你是被 count 锁住、被 cpu_init 锁住、还是被中断上下文锁住，都算"抢占已关"。这样 `preempt_enable` 的判断逻辑也简单：count 减到 0 才开中断，而 cpu_init/in_interrupt/abort_kernel 这些高位不会被 `preempt_enable` 动到。

## 2. `boot_cpu_cold_init`：建 per-CPU 骨架

这一节是本课的第一个主战场。`boot_cpu_cold_init` 上的 handler 干的事都是**初始化 per-CPU 的软件数据结构**：CPULOCAL 数组、per-CPU 对象、per-CPU 状态字段。

### 2.1 `cpulocal`（priority first）：设 CPU index

`hyp/core/cpulocal/cpulocal.ev`：

```text
// This needs to run first to set up the correct CPU number before the rest of
// the handlers run.
subscribe boot_cpu_cold_init
	priority first
```

注释直接点明：**必须 first，因为它要设 CPU 号，后面所有 handler 都要用**。

`hyp/core/cpulocal/src/cpulocal.c`：

```c
void
cpulocal_handle_boot_cpu_cold_init(cpu_index_t cpu)
{
	thread_t *self = thread_get_self();
	assert_safety(self != NULL);

	// Ensure that the index is set early on the primary idle thread
	self->cpulocal_current_cpu = cpulocal_check_index(cpu);

	// This is the earliest point at which we can call TRACE(), so let's
	// do that now to let debuggers know that the CPU is coming online.
	TRACE_LOCAL(DEBUG, INFO, "CPU {:d} coming online", cpu);
}
```

逐段拆解：

1. **`thread_get_self()`**：拿到当前线程。冷启动时这就是上一课讲的 idle 线程（在 `boot_runtime_first_init` 就建好的那个"半成品"）。
2. **`self->cpulocal_current_cpu = cpulocal_check_index(cpu)`**：把传入的 CPU index 写进当前线程的 `cpulocal_current_cpu` 字段。这个字段就是后面 `cpulocal_get_index()` 读的地方——所有"我是哪个 CPU"的查询都走它。
3. **`TRACE_LOCAL(DEBUG, INFO, "CPU {:d} coming online", cpu)`**：注释明确说"这是能调 TRACE 的最早点"。为什么是这里？因为 `TRACE` 需要知道"现在是哪个 CPU 在说话"，而 CPU 号刚刚才被写进线程——写之前调 TRACE，CPU 号是 `CPU_INDEX_INVALID`，日志会乱。

要点：
- `cpulocal` 是 `first`，因为**后面所有 handler 都可能用 `cpulocal_get_index()` 或 `CPULOCAL(...)`**，而那俩读的就是 `cpulocal_current_cpu`。不 first 的话，别人读到的是 `CPU_INDEX_INVALID`。
- 这一步**只是写一个数字到线程的一个字段**，没有分配、没有建数据结构——因为此刻 allocator 还在 `boot_cold_init` 阶段刚建好，per-CPU 数据要靠后面的 handler 自己建。

> 类比：`cpulocal` first 就像开工前先给每个工人发工牌。工牌上写"你是几号"。后面所有工种（handler）都要看工牌才知道自己在哪个工位干活。不发工牌就开工，大家都以为自己是 0 号。

### 2.2 `gicv3`（priority 10）：redistributor 初始化

`hyp/platform/gicv3/gicv3.ev`：

```text
// Since other modules might be enabling their hardware interrupts in
// cpu_cold_init, we need to make sure GIC's handler for this event runs before
// the handlers of the other modules.
subscribe boot_cpu_cold_init
	priority 10
```

注释点明了依赖：**别的模块可能在 `cpu_cold_init` 里就 enable 自己的硬件中断，所以 GIC 必须先跑**（priority 10，比默认的 0 早），把 redistributor 准备好，否则别人 enable 一个还没就绪的 IRQ 会出事。

`hyp/platform/gicv3/src/gicv3.c`：

```c
void
gicv3_handle_boot_cpu_cold_init(cpu_index_t cpu)
{
	gicr_t *gicr = CPULOCAL_BY_INDEX(gicr_cpu, cpu).gicr;

	// Configure all interrupts to the default priority
	for (irq_t i = GIC_SGI_BASE; i < GIC_PPI_BASE; i++) {
		atomic_store_relaxed(&gicr->sgi.ipriorityr[i],
				     GIC_PRIORITY_DEFAULT);
	}
	for (irq_t i = GIC_PPI_BASE; i < GIC_SPI_BASE; i++) {
		atomic_store_relaxed(&gicr->sgi.ipriorityr[i],
				     GIC_PRIORITY_DEFAULT);
	}
	// ... 扩展 PPI 优先级、ProcessorSleep、LPI base 等 ...

	// Disable all local IRQs
	atomic_store_relaxed(&gicr->sgi.icenabler0, 0xffffffffU);
	gicr_wait_for_write(gicr);
	// ... Enable 1-of-N targeting、LPI base 等 ...
}
```

逐段拆解：

1. **`CPULOCAL_BY_INDEX(gicr_cpu, cpu).gicr`**：从 per-CPU 数组里取出**本 CPU 对应的 redistributor** 指针。GICv3 的 redistributor 是 per-CPU 的——每个 CPU 有自己专属的 GICR 寄存器块。这个映射关系在 `boot_cold_init`（上一课的全局阶段）就建好了，这里只是取出来用。
2. **配 SGI/PPI 优先级**：把本 CPU 的所有 SGI（0–15）和 PPI（16–31）都设成默认优先级。SPI 是全局的，在 `irq_init`（上一课的 `boot_cold_init` 阶段）已经配过；PPI 是 per-CPU 的，必须每个 CPU 自己配。
3. **`icenabler0 = 0xffffffffU`**：先**关掉本 CPU 所有本地中断**。这是"建骨架"思路的体现：先把所有 IRQ 关掉，等后面 `boot_cpu_warm_init` / `boot_hypervisor_start` 各模块真正要用某个 IRQ 时再单独 enable。

要点：
- GICv3 的 GICD（distributor）是全局的，在 `irq_init`（`boot_cold_init` 阶段）配一次；GICR（redistributor）是 per-CPU 的，必须在 `boot_cpu_cold_init` 里**每个 CPU 自己配**。
- `priority 10` 是为了赶在"别人 enable 自己的 IRQ"之前——GICR 没就绪就 enable，等于没 enable。
- 这里只配 per-CPU 的 SGI/PPI/LPI；SPI 路由在全局阶段就配好了。

> 类比：GICD 是小区总配电箱（一栋楼一个），GICR 是每户的电表箱（每家一个）。总配电箱在上一课已经配好；这一步是给你家装好电表箱、把所有分闸先拉下。后面哪个房间要用电，再去合那个房间的闸。

### 2.3 其他默认优先级的订阅者：per-CPU 数组清零

除了 `cpulocal(first)` 和 `gicv3(10)`，`boot_cpu_cold_init` 上还有一批**默认优先级（0）**的订阅者。它们大多在干同一件事：**初始化某个 per-CPU 数组**。举两个典型：

**`arm_vm_timer`**（`hyp/vm/arm_vm_timer/aarch64/src/arm_vm_timer.c`）：

```c
void
arm_vm_timer_handle_boot_cpu_cold_init(void)
{
	for (int tt = ENUM_ARM_VM_TIMER_TYPE_MIN_VALUE;
	     tt < ARM_VM_TIMER_TYPE_NUM; tt++) {
		atomic_init(&CPULOCAL(arm_vm_timer_irq_active)[tt], false);
	}
}
```

把本 CPU 的 `arm_vm_timer_irq_active`（虚拟/物理定时器 IRQ 是否激活）数组清零。这是 per-CPU 状态，每个 CPU 自己清自己那份。

**`vcpu_aarch64`**（`hyp/vm/vcpu/armv8-64/`，代码生成模板）：

```c
void
vcpu_arch_handle_boot_cpu_cold_init(cpu_index_t cpu)
{
	// 探测 CPU 是否支持 ECBHB/CLRBHB，选对应的 VCPU 异常向量表
	CPULOCAL_BY_INDEX(vcpu_aarch64_vectors, cpu) =
		(uintptr_t)&vcpu_aarch64_vectors;
	// ...
}
```

把本 CPU 用的 VCPU 异常向量表基地址写进 per-CPU 数组。每个 CPU 跑 VCPU 时要用自己那份向量表。

**`psci`**（`hyp/vm/psci/src/psci_common.c`）：

```c
void
psci_handle_boot_cpu_cold_init(cpu_index_t cpu)
{
	atomic_store_relaxed(&CPULOCAL_BY_INDEX(vpm_active_vcpus, cpu), 0U);
	(void)psci_set_vpm_active_pcpus_bit(cpu);
}
```

把本 CPU 的"活跃 VCPU 计数"清零，并把自己标记到 vpm active pcpus 位图里。

要点：
- 这些默认优先级的 handler **共同点**：都在初始化某个 `CPULOCAL_*` 数组的本 CPU 那一项。
- 它们之间没有强依赖（同优先级顺序未定义），所以谁先谁后无所谓——每个 handler 只动自己那个数组，不碰别人的。
- 它们**必须排在 `cpulocal(first)` 之后**：因为都用了 `CPULOCAL(...)` 宏，而那个宏内部调 `cpulocal_get_index()`，得先有 CPU 号。

### 2.4 `boot_cpu_cold_init` 优先级总表

把本节涉及的 handler 按执行顺序排出来（`first` 最先，`last` 最后，数字大的比数字小的先跑）：

| 顺序 | 优先级 | handler | 模块 | 干的事 |
|------|--------|---------|------|--------|
| 1 | first | `cpulocal_handle_boot_cpu_cold_init` | cpulocal | 写 CPU index 到当前线程，从此能 TRACE |
| 2 | 10 | `gicv3_handle_boot_cpu_cold_init` | gicv3 | 配本 CPU 的 redistributor（SGI/PPI 优先级、关本地 IRQ、LPI base） |
| 3 | 0（默认） | `arm_vm_timer_handle_boot_cpu_cold_init` | arm_vm_timer | 清零本 CPU 的定时器 IRQ 激活标志 |
| 4 | 0（默认） | `vcpu_arch_handle_boot_cpu_cold_init` | vcpu_aarch64 | 选并写本 CPU 的 VCPU 异常向量表 |
| 5 | 0（默认） | `psci_handle_boot_cpu_cold_init` | psci | 清零本 CPU 的活跃 VCPU 计数 |
| … | 0（默认） | （platform_pmu / platform_timer / vfp / vdebug / ete / vetm / vtrbe / soc_qemu …） | … | 各自 per-CPU 状态初始化 |

> 说明：同优先级（这里都是 0）的 handler 之间顺序未定义，所以 3–5 的先后不固定；但它们都排在 `cpulocal(first)` 和 `gicv3(10)` 之后。

### 2.5 为什么是这个顺序——依赖链

![boot_cpu_cold_init 依赖链](图/第3课-cold依赖链.svg)

读法：箭头表示"右边依赖左边"。`cpulocal` 是地基（没它别人不知道自己在哪个 CPU），`gicv3` 是配电（没它别人 enable IRQ 没用），默认那批是各房间装修（各动各的 CPULOCAL 数组，互不干扰）。

## 3. `boot_cpu_warm_init`：通电（重新初始化硬件寄存器）

这一节是本课的第二个主战场。`boot_cpu_warm_init` 上的 handler 干的事都是**写硬件系统寄存器、enable 本地 IRQ**——每次 CPU 上电都要重做一遍，因为硬件寄存器在断电后状态会丢失。

### 3.1 `power`（priority first）：等 CPU 真正上电

`hyp/core/power/power.ev`：

```text
subscribe boot_cpu_warm_init
	priority first
	require_preempt_disabled
```

`hyp/core/power/src/power.c`：

```c
void
power_handle_boot_cpu_warm_init(void)
{
	spinlock_acquire_nopreempt(&CPULOCAL(power_voting).lock);

	while (CPULOCAL(power_state) == CPU_POWER_STATE_OFF) {
		spinlock_release_nopreempt(&CPULOCAL(power_voting).lock);
		spinlock_acquire_nopreempt(&CPULOCAL(power_voting).lock);
	}

	cpu_power_state_t state = CPULOCAL(power_state);
	assert((state == CPU_POWER_STATE_COLD_BOOT) ||
	       (state == CPU_POWER_STATE_STARTED) ||
	       (state == CPU_POWER_STATE_SUSPEND));
	CPULOCAL(power_state) = CPU_POWER_STATE_ONLINE;
	// ... 触发 power_cpu_online、更新 online 计数 ...
}
```

逐段拆解：

1. **`while (CPULOCAL(power_state) == CPU_POWER_STATE_OFF)`**：一个忙等循环——如果本 CPU 的 power_state 还是 `OFF`，就反复松锁/加锁等。等什么？等别的 CPU 把它改成 `STARTED`（即别的 CPU 调 `power_vote_cpu_on` 把它拉起来）。这是为了处理"CPU 被投票上电但还没真正完成上电"的竞态。
2. **`CPULOCAL(power_state) = CPU_POWER_STATE_ONLINE`**：确认本 CPU 已经在线，把状态改成 `ONLINE`。
3. **触发 `power_cpu_online` 事件**：通知其他模块"我上线了"。

要点：
- `power` 是 `first`，因为**后面所有 handler 都假定 CPU 已经在线**。如果 power 还没跑完，别人就动手配硬件，可能配到一个还没真正通电的 CPU 上。
- 这里用 `CPULOCAL(power_state)`——读 per-CPU 数组，所以**必须排在 `cpulocal(first)` 之后**（在 `boot_cpu_cold_init` 阶段）。但 `boot_cpu_warm_init` 本身一定在 `boot_cpu_cold_init` 之后跑，所以这里能安全用 `CPULOCAL`。

> 类比：`power` first 就像搬进新家前先确认电表通了、总闸推上了。没确认就开灯，可能白开（没电）或者跳闸。等电表确认 OK，后面才能放心接各种电器。

### 3.2 `debug`（priority 500）：解除 OS 锁

`hyp/core/debug/aarch64/debug.ev`：

```text
// High priority to permit debugger to attach as early as possible
subscribe boot_cpu_warm_init
	priority 500
```

`hyp/core/debug/aarch64/src/debug.c`：

```c
void
debug_handle_boot_cpu_warm_init(void)
{
	debug_os_unlock();
}

static void
debug_os_unlock(void)
{
	OSLAR_EL1_t oslar = OSLAR_EL1_default();
	OSLAR_EL1_set_oslk(&oslar, false);
	register_OSLAR_EL1_write_ordered(oslar, &debug_asm_order);
	OSDLR_EL1_t osdlr = OSDLR_EL1_default();
	OSDLR_EL1_set_dlk(&osdlr, false);
	register_OSDLR_EL1_write_ordered(osdlr, &debug_asm_order);
	asm_context_sync_ordered(&debug_asm_order);
}
```

逐段拆解：

1. **`OSLAR_EL1_set_oslk(&oslar, false)`**：清 OSLAR_EL1 的 OS 锁位。OS 锁一锁上，所有 EL1 的调试寄存器访问都会触发 trap——外部调试器就挂不上。
2. **`OSDLR_EL1_set_dlk(&osdlr, false)`**：清 OSDLR_EL1 的 double lock 位。double lock 是更深层的锁，锁上后整个 debug 状态都被冻结。

要点：
- `priority 500`（很高）是为了让调试器**尽早**能挂上。注释直接写了"permit debugger to attach as early as possible"。
- 这一步只写两个系统寄存器，非常轻；但意义大——不解锁，调试器全程挂不上，启动出问题只能干瞪眼。

### 3.3 `rcu_bitmap`（priority 100）：激活当前 CPU

`hyp/core/rcu_bitmap/rcu.ev`：

```text
// Events that activate a CPU. These all run early so handlers with RCU
// readers will run after the CPU is active.
subscribe boot_cpu_warm_init
	handler rcu_bitmap_activate_current()
	priority 100
	require_preempt_disabled
```

`hyp/core/rcu_bitmap/src/rcu_bitmap.c`：

```c
void
rcu_bitmap_activate_current(void)
{
	assert_cpulocal_safe();
	cpu_index_t cpu = cpulocal_get_index();
	rcu_bitmap_activate_cpu(cpu);
}

static void
rcu_bitmap_activate_cpu(cpu_index_t cpu_index) REQUIRE_PREEMPT_DISABLED
{
	uint32_t cpu_bit = (uint32_t)util_bit(cpu_index);
	rcu_cpu_state_t *my_state = &CPULOCAL_BY_INDEX(rcu_state, cpu_index);

	if (compiler_unexpected(!my_state->is_active)) {
		my_state->is_active = true;
		(void)atomic_fetch_or_explicit(&rcu_state.active_cpus, cpu_bit,
					       memory_order_relaxed);
		atomic_thread_fence(memory_order_seq_cst);
	}
}
```

逐段拆解：

1. **`cpulocal_get_index()`**：拿到当前 CPU 号。
2. **`my_state->is_active = true`**：标记本 CPU 在 RCU 的"活跃 CPU 集合"里。
3. **`atomic_fetch_or_explicit(&rcu_state.active_cpus, cpu_bit, ...)`**：把本 CPU 的位写进全局 `active_cpus` 位图。RCU 的 grace period（宽限期）靠这个位图判断"还有哪些 CPU 没表态"。
4. **`atomic_thread_fence(memory_order_seq_cst)`**：一个全屏障，保证"我已加入活跃集合"这件事对其他 CPU 可见，且在后续任何 RCU 读临界区之前完成。

要点：
- RCU（Read-Copy-Update）是一种延迟回收机制。一个 CPU 要做 RCU 读操作前，必须先把自己标记为"活跃"，否则 grace period 不会等它，可能在它还在读的时候就把数据回收了。
- `priority 100` 是为了**赶在所有用 RCU 读的 handler 之前**。注释明确："handlers with RCU readers will run after the CPU is active"。
- 冷启动时 `boot_cold_init` 阶段（上一课）已经调过一次 `rcu_bitmap_handle_boot_cold_init`（priority 100）激活 Boot CPU；这里 `boot_cpu_warm_init` 再调一次，是为了热启动场景——热启动不跑 `boot_cpu_cold_init`，所以必须在 `boot_cpu_warm_init` 里补激活。

> 类比：RCU 像一个需要全员签到的会议。每个 CPU 进会场（上电）后要先在签到表上画勾（`rcu_bitmap_activate_cpu`），会议主持（grace period）才会在等齐所有人后开始回收旧资料。不签到就坐下来听会，主持可能以为你不在，直接把你要看的资料销毁了。

### 3.4 `partition_phys_access`（priority 10）：PAN 位

`hyp/core/partition_standard/armv8/phys_access.ev`：

```text
subscribe boot_cpu_warm_init
	handler partition_phys_access_cpu_warm_init()
	priority 10
```

`hyp/core/partition_standard/armv8/src/phys_access.c`：

```c
void
partition_phys_access_cpu_warm_init(void)
{
#if ARCH_AARCH64_USE_PAN
	__asm__ volatile("msr PAN, 1" ::: "memory");
#else
	// Nothing to do here.
#endif
}
```

逐段拆解：

1. **`msr PAN, 1`**：开启 PAN（Privileged Access Never）。PAN 是 ARMv8 的一个安全特性：开了之后，EL1/EL2 的特权代码**不能直接访问用户态映射的内存**，必须显式地临时关 PAN 才行。
2. **`priority 10`**：比较基础，要在大多数默认 handler 之前把 PAN 打开，防止后面有人误碰用户态内存。

要点：
- 这一步只写一个系统寄存器位，但它是**安全基线**：PAN 不开，hypervisor 的特权代码可能意外写到 guest 的内存里。
- 注意它和 `power(first)` / `debug(500)` / `rcu(100)` 的优先级关系：`10` 比它们都晚，但比默认的 `0` 早。

### 3.5 默认优先级的订阅者：enable 本地 IRQ + 系统寄存器

默认优先级（0）的 handler 是 `boot_cpu_warm_init` 上数量最多的一批，它们干的都是"具体某个硬件模块在本 CPU 上的寄存器初始化 + enable 本地 IRQ"。举三个典型：

**`gicv3`**（`hyp/platform/gicv3/src/gicv3.c`）：

```c
void
gicv3_handle_boot_cpu_warm_init(void)
{
	// Enable system register access and disable FIQ/IRQ bypass
	ICC_SRE_EL2_t icc_sre = ICC_SRE_EL2_default();
	ICC_SRE_EL2_set_SRE(&icc_sre, true);
	register_ICC_SRE_EL2_write_ordered(icc_sre, &gic_init_order);
	asm_context_sync_ordered(&gic_init_order);

	// Configure PMR to allow all interrupt priorities
	ICC_PMR_EL1_set_Priority(&icc_pmr, 0xff);

	// Set EOImode to 1, so we can drop priority before delivery to VMs
	ICC_CTLR_EL1_set_EOImode(&icc_ctrl, true);

	// Enable group 1 interrupts
	ICC_IGRPEN_EL1_set_Enable(&icc_grpen1, true);

	// Enable the SGIs used by IPIs
	atomic_store_release(&gicr->sgi.isenabler0, 0x1);
}
```

注意：`boot_cpu_cold_init` 里的 gicv3 是配 **GICR（redistributor）**；这里 `boot_cpu_warm_init` 里的 gicv3 是配 **ICC_*（CPU interface，CPU 侧的 GIC 系统寄存器）**。redistributor 是"中断怎么分发到这个 CPU"，CPU interface 是"这个 CPU 怎么收中断"。前者是数据结构，后者是硬件寄存器——正好对应 cold/warm 的分工。

**`vgic`**（`hyp/vm/vgic/src/deliver.c`）：

```c
void
vgic_handle_boot_cpu_warm_init(void)
{
	if (vgic_maintenance_hwirq != NULL) {
		irq_enable_local(vgic_maintenance_hwirq);
	}
	// Ensure that EL1 has SRE=1 set
	ICC_SRE_EL1_set_SRE(&icc_sre, true);
	register_ICC_SRE_EL1_write(icc_sre);
}
```

`vgic_maintenance_hwirq` 是在 `boot_hypervisor_start`（下一课）里分配的"VGIC 维护中断"。热启动时这个 hwirq 已经存在（全局对象），但本 CPU 的 GICR 上还没 enable 它，所以这里 `irq_enable_local` 把它在本 CPU 打开。

**`platform_timer` / `arm_vm_timer`**：

```c
// platform_timer
void
platform_timer_handle_boot_cpu_warm_init(void)
{
	if (hyp_timer_hwirq != NULL) {
		irq_enable_local(hyp_timer_hwirq);
	}
}

// arm_vm_timer
void
arm_vm_timer_handle_boot_cpu_warm_init(void)
{
	arm_vm_timer_init(ARM_VM_TIMER_TYPE_VIRTUAL);
	arm_vm_timer_init(ARM_VM_TIMER_TYPE_PHYSICAL);
	// 配 CNTHCTL_EL2：允许 EL1 访问虚拟/物理定时器
}
```

定时器 IRQ 也是全局对象（在 `boot_hypervisor_start` 分配），但每个 CPU 上电后要 `irq_enable_local` 在本 CPU 的 GICR 上打开它。

要点：
- 默认那批 handler 的**共同模式**：`irq_enable_local(某个全局 hwirq)` + 写几个本 CPU 的系统寄存器。
- 它们排在 `power(first)` / `debug(500)` / `rcu(100)` / `partition_phys_access(10)` 之后，因为这些是更基础的前提。
- 它们**能直接用** `irq_enable_local`，是因为 `gicv3_handle_boot_cpu_cold_init`（priority 10，在 `boot_cpu_cold_init` 阶段）已经把 GICR 配好了——cold 建骨架，warm 才能通电。

### 3.6 `boot_cpu_warm_init` 优先级总表

| 顺序 | 优先级 | handler | 模块 | 干的事 |
|------|--------|---------|------|--------|
| 1 | first | `power_handle_boot_cpu_warm_init` | power | 等 CPU 真正上电，状态转 ONLINE，触发 power_cpu_online |
| 2 | 500 | `debug_handle_boot_cpu_warm_init` | debug | 解 OS 锁，让调试器能尽早挂上 |
| 3 | 100 | `rcu_bitmap_activate_current` | rcu_bitmap | 把本 CPU 加进 RCU 活跃集合 |
| 4 | 10 | `partition_phys_access_cpu_warm_init` | partition_phys_access | 开 PAN 位 |
| 5 | 0（默认） | `gicv3_handle_boot_cpu_warm_init` | gicv3 | 配 ICC_*（CPU interface）、enable IPI SGI |
| 6 | 0（默认） | `vgic_handle_boot_cpu_warm_init` | vgic | enable VGIC 维护 IRQ、设 EL1 SRE |
| 7 | 0（默认） | `platform_timer_handle_boot_cpu_warm_init` | arm_arch_timer | enable hyp 定时器 IRQ |
| 8 | 0（默认） | `arm_vm_timer_handle_boot_cpu_warm_init` | arm_vm_timer | 初始化虚拟/物理定时器、配 CNTHCTL_EL2 |
| … | 0（默认） | （arch sysreg_init / vfp / vcpu_aarch64 / platform_pmu / vete / vetm / vdebug / sve / mpam …） | … | 各自本 CPU 系统寄存器初始化 |

> 说明：同优先级（0）的 handler 顺序未定义；但都排在 `power(first)` / `debug(500)` / `rcu(100)` / `partition_phys_access(10)` 之后。

### 3.7 为什么是这个顺序——依赖链

![boot_cpu_warm_init 依赖链](图/第3课-warm依赖链.svg)

读法：从左到右是"越来越具体"的初始化。左边是前提（CPU 在线、能调试、RCU 激活、安全基线），右边是具体硬件（GIC CPU interface、定时器、VGIC）。每一步都假定左边已经做完。

## 4. 为什么 `boot_cpu_cold_init` 之后才能 TRACE

回头看 `boot.c`：

```c
trigger_boot_cpu_early_init_event();
trigger_boot_cold_init_event(cpu);
trigger_boot_cpu_cold_init_event(cpu);

// It's safe to log now.
TRACE_AND_LOG(ERROR, WARN, "Hypervisor cold boot, version: {:s} ({:s})",
	      (register_t)hypervisor_version,
	      (register_t)hypervisor_build_date);
```

注释"// It's safe to log now"就在 `boot_cpu_cold_init` 之后。为什么？因为 `TRACE` 内部需要两个东西：

1. **CPU index**：`TRACE` 要在日志里标"这是哪个 CPU 说的"。这个号由 `cpulocal_handle_boot_cpu_cold_init`（`boot_cpu_cold_init` 的 `first`）写入线程。在那之前，`cpulocal_current_cpu` 是 `CPU_INDEX_INVALID`，`TRACE` 拿不到合法 CPU 号。
2. **preempt count**：`TRACE` 走的日志路径可能碰 `preempt_disable`/`preempt_enable`，需要 preempt 计数器已经合法。这个由 `boot_runtime_first_init`（汇编阶段）建 idle 线程时初始化好。

`boot.c` 顶部的注释直接写了：

```c
// We can't trace/log early because the CPU index and preemption count
// in the thread are still uninitialized.
```

所以时间线是：

![为什么 boot_cpu_cold_init 之后才能 TRACE](图/第3课-TRACE时间线.svg)

`cpulocal` 在 `boot_cpu_cold_init` 的 `first` 跑完，CPU index 就就绪了；所以 `boot_cpu_cold_init` 整条链跑完之后，`TRACE_AND_LOG` 才安全。这就是为什么第一句 log 出现在那个位置。

> 注意：`cpulocal_handle_boot_cpu_cold_init` 内部自己就调了一句 `TRACE_LOCAL`——那是整个系统里**第一句**合法的 TRACE，因为它就在写完 CPU index 之后。在那之前的所有代码都不能 TRACE。

## 5. CPULOCAL 机制：软件 CPU-local storage

本课反复出现 `CPULOCAL(...)` 和 `CPULOCAL_BY_INDEX(...)`，这里把它讲清楚。

### 5.1 为什么需要 CPULOCAL

ARM64 没有一个"方便读的 CPU index 寄存器"（不像 x86 有 GS base 之类的）。Gunyah 用**软件模拟**的 CPU-local storage：开一个大小为 `PLATFORM_MAX_CORES` 的数组，每个 CPU 用自己的 index 当下标去访问"自己那份"。

`hyp/interfaces/cpulocal/include/cpulocal.h`：

```c
// 声明：extern type cpulocal_##name[PLATFORM_MAX_CORES]
#define CPULOCAL_DECLARE_EXTERN(type, name)
// 定义：type cpulocal_##name[PLATFORM_MAX_CORES]
#define CPULOCAL_DECLARE(type, name)        type cpulocal_##name[PLATFORM_MAX_CORES]
#define CPULOCAL_DECLARE_STATIC(type, name) static type cpulocal_##name[PLATFORM_MAX_CORES]

// 访问"当前 CPU 那一份"
#define CPULOCAL(name)              cpulocal_##name[cpulocal_get_index()]
// 访问"指定 index 那一份"
#define CPULOCAL_BY_INDEX(name, i)  cpulocal_##name[cpulocal_check_index(i)]
```

读法：
- `CPULOCAL_DECLARE(power_voting_t, power_voting)` 定义一个数组 `cpulocal_power_voting[PLATFORM_MAX_CORES]`。
- `CPULOCAL(power_voting)` 展开成 `cpulocal_power_voting[cpulocal_get_index()]`——访问**当前 CPU** 的那项。
- `CPULOCAL_BY_INDEX(power_voting, 3)` 展开成 `cpulocal_power_voting[3]`——访问 **3 号 CPU** 的那项（启动期常这么用，因为"当前 CPU"还不一定是目标 CPU）。

### 5.2 `cpulocal_get_index` 从哪读

```c
static inline cpu_index_t
cpulocal_get_index(void) REQUIRE_PREEMPT_DISABLED
{
	return cpulocal_check_index(cpulocal_get_index_unsafe());
}

cpu_index_t
cpulocal_get_index_unsafe(void)
{
	const thread_t *self = thread_get_self();
	return cpulocal_get_index_for_thread(self);
}

cpu_index_t
cpulocal_get_index_for_thread(const thread_t *thread)
{
	return thread->cpulocal_current_cpu;
}
```

就是读当前线程的 `cpulocal_current_cpu` 字段——也就是 `cpulocal_handle_boot_cpu_cold_init` 写进去的那个值。

### 5.3 为什么要 `REQUIRE_PREEMPT_DISABLED`

`cpulocal_get_index()` 带了 `REQUIRE_PREEMPT_DISABLED`。因为：如果抢占开着，当前线程可能被调度到别的 CPU 上，那读出来的 CPU index 就可能"读到一半就过期了"。所以访问 CPULOCAL 必须在抢占关的临界区里。

这也是为什么本课里所有 `boot_cpu_warm_init` 上的 handler 都隐含 `require_preempt_disabled`——因为整条启动链被 preempt 的 `cpu_init` 位锁着（第 1 节），preempt 一直是关的，CPULOCAL 访问才安全。

### 5.4 上下文切换时谁来更新它

`cpulocal_handle_thread_context_switch_post`（`priority first`）：

```c
void
cpulocal_handle_thread_context_switch_post(thread_t *prev)
{
	thread_t *self = thread_get_self();
	cpu_index_t this_cpu = CPU_INDEX_INVALID;
	// ... 根据 prev 和 self 算出 this_cpu ...
	prev->cpulocal_current_cpu = CPU_INDEX_INVALID;
	self->cpulocal_current_cpu = this_cpu;
}
```

每次线程切换后，新线程的 `cpulocal_current_cpu` 被更新成"现在跑在哪个 CPU"。这样 `CPULOCAL(...)` 永远拿到的是"当前线程当前所在 CPU"的那份数据。

> 类比：CPULOCAL 是一排更衣柜，每个 CPU 一格。`cpulocal_current_cpu` 是你手里的钥匙牌，写着"你现在是几号柜"。每次换班（上下文切换）时，老员工把钥匙牌清空（`CPU_INDEX_INVALID`），新员工拿到写着自己工号的新牌。你取东西（`CPULOCAL(...)`）时，先看牌（`cpulocal_get_index`），再去对应的柜子拿。换班期间不能取东西（必须 `preempt_disabled`），否则可能拿到别人的柜子。

## 6. `boot_cpu_start`：preempt 解锁

启动链的最后一步是 `trigger_boot_cpu_start_event()`。这条链上目前也只有一个订阅者：`preempt`，而且是 `priority last`。

```text
subscribe boot_cpu_start
	priority last
	release_preempt_disabled
```

```c
void
preempt_handle_boot_cpu_start(void) LOCK_IMPL
{
	// Boot has finished; allow preemption to be enabled.
	assert((preempt_disable_count & preempt_cpu_init) != 0U);
	preempt_disable_count &= ~preempt_cpu_init;
}
```

这一步把第 1 节设上的 `cpu_init` 位清掉。从这一刻起，`preempt_enable()` 才真正可能把 count 减到 0 并开中断。

`priority last` 保证它是 `boot_cpu_start` 事件链上**最后一个** handler——前面所有 handler 都跑完，才解锁。这样整条启动链（early → ... → start）从头到尾都被 `cpu_init` 位锁住，期间任何 `preempt_enable` 都不会真正开抢占。

时间线：

![preempt 启动锁时间线](图/第3课-启动锁.svg)

解锁之后，`boot_cold_init` 紧接着调 `thread_boot_set_idle()`，切到 idle 线程进入 `idle_loop()`。idle 循环里会 `preempt_enable` / `scheduler_yield`——这时抢占才真正能发生，调度器才能把 VCPU 线程调度上来。

> 注意：`boot_warm_init`（热启动）结尾不是 `thread_boot_set_idle`，而是 `thread_boot_restore_frozen`——它恢复的是"被冻结的当前线程栈"（休眠前正在跑的那个线程），而不是 idle。因为热启动是从休眠中醒来，应该回到休眠前的地方继续跑，而不是回到 idle。

把本课讲的所有事件按时间顺序画出来，标上每一步的关键订阅者：

![per-CPU 启动链全景](图/第3课-启动链全景.svg)

### 7.1 三个关键时间点

1. **`cpulocal(first)` 跑完**：CPU index 就位，`TRACE_LOCAL` 第一次可用（但 `TRACE_AND_LOG` 要等整条 `boot_cpu_cold_init` 跑完）。
2. **`boot_cpu_cold_init` 整条跑完**：per-CPU 软件骨架全部就位（GICR、CPULOCAL 数组、vcpu 向量表、psci 计数）。`boot.c` 在这里打第一句 `TRACE_AND_LOG`。
3. **`boot_cpu_start(last)` 跑完**：preempt 启动锁解除，调度器可以开始工作，idle 循环能 yield 出去。

### 7.2 cold 和 warm 的分工（再次强调）

| | `boot_cpu_cold_init`（建骨架） | `boot_cpu_warm_init`（通电） |
|---|---|---|
| 跑的时机 | 只冷启动 | 每次上电（含冷启动） |
| 干的事 | 初始化 per-CPU 软件数据结构 | 写硬件系统寄存器、enable 本地 IRQ |
| 典型 handler | cpulocal / gicv3(GICR) / arm_vm_timer(清零) / vcpu(向量表) / psci(计数) | power / debug / rcu / gicv3(CPU interface) / vgic / timer(enable IRQ) |
| 是否分配对象 | 是（CPULOCAL 数组初始化、per-CPU 状态） | 否（用 cold 阶段已建好的对象，只是 enable） |

一句话：**cold 建"账"，warm 开"闸"**。冷启动既建账又开闸；热启动只开闸（账还在）。

---

## 本课你要带走的三句话

1. **cold vs warm**：`boot_cpu_cold_init` = 建 per-CPU 骨架（只冷启动）；`boot_cpu_warm_init` = 通电、写硬件寄存器、enable IRQ（每次上电）。冷启动两件都做，热启动只做 warm。
2. **两个 `first`**：`cpulocal` 是 `boot_cpu_cold_init` 的 `first`（后面所有人都要 CPU 号）；`power` 是 `boot_cpu_warm_init` 的 `first`（后面所有人假定 CPU 已在线）。
3. **preempt 启动锁**：`boot_cpu_early_init` 置 `cpu_init` 位、`boot_cpu_start(last)` 清掉，整条启动链被这把锁锁住，期间 `preempt_enable` 不会真正开抢占。这就是为什么启动期不怕被抢占切走。
