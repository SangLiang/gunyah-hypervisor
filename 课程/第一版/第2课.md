# 第 2 课 · L1 启动链第二段：`boot_cold_init` 的关键订阅者

按学习地图：上一课跟到 `boot_cold_init(cpu)` 的 `trigger_*` 总序；今天打开这条链上**最关键的三个订阅者**——`partition` / `memdb` / `idle(thread)`——看"模块拼装"在代码里到底长什么样。

> 本课目标：能说清**谁先跑、谁后跑、为什么这个顺序**，并能用一句话讲清"一页内存在启动期归谁管"。

---

## 0. 先对齐：上一课的事件链回顾

`hyp/core/boot/src/boot.c` 的 `boot_cold_init()`：

```c
trigger_boot_cpu_early_init_event();
trigger_boot_cold_init_event(cpu);      // ← 本课主战场
trigger_boot_cpu_cold_init_event(cpu);
// 此后可 log
trigger_boot_cpu_warm_init_event();
trigger_boot_hypervisor_start_event();
trigger_boot_cpu_start_event();
thread_boot_set_idle();                 // 不再返回
```

### 0.1 `trigger_*` 到底干了什么

很多人看到 `trigger_boot_cold_init_event(cpu)` 会以为"调用一个函数"——**不是**。它更像一个广播台：把"boot_cold_init 事件发生了"这个消息广播给所有订阅者，订阅者们按预先排好的顺序一个接一个被调用。

打个比方：`trigger_*` 是**点名**，被点到的人（handler）按事先排好的座次一个个站起来发言。点名本身不做事，做事的是被点到的人。

### 0.2 订阅关系写在哪儿

订阅关系不在 C 代码里写 `register_callback(...)`，而是写在**每个模块自己的 `*.ev` 文件**里。构建系统（`tools/events/`）在编译期扫描这些 `.ev` 文件，自动生成一张分发表（函数指针表），运行时 `trigger_*` 就按这张表逐项调用。

这样做的好处：
- **模块解耦**：`boot.c` 不需要 `#include` partition 的头文件才能调 partition 的初始化；partition 自己在 `.ev` 里声明"我要订阅 boot_cold_init"。
- **顺序显式**：谁先谁后写在 `.ev` 的 `priority` 字段里，一眼可见，不用翻代码追调用链。
- **可扩展**：新增一个模块只要新写一个 `.ev`，不动 `boot.c` 一行代码。

本课只跟 `boot_cold_init` 这一条事件上的三个订阅者（partition / memdb / idle）。

## 1. "模块拼装"的合同：`.ev` 文件长什么样

Gunyah 的事件驱动是**编译期拼装**：模块在自己的 `*.ev` 里 `subscribe` 某个事件，构建系统（`tools/events/`）会生成一张分发表，运行时 `trigger_*` 按优先级逐个调用。

### 1.1 `.ev` 文件的基本语法

`.ev` 是一种 DSL（领域专用语言），核心关键字只有几个：

| 关键字 | 作用 | 例子 |
|--------|------|------|
| `subscribe <事件名>` | 声明"我要订阅这个事件" | `subscribe boot_cold_init()` |
| `handler <函数名>` | 指定被调用的函数（省略时按命名约定生成） | `handler partition_standard_boot_add_private_heap()` |
| `priority <值>` | 指定调用顺序，数字越大越晚；`first`/`last` 是极端 | `priority 9` |
| `unwinder <函数名>` | 失败回滚函数（见 1.4） | `unwinder(owner, phys_base, size)` |

> **命名约定**：如果省略 `handler`，代码生成器会按 `<module>_handle_<event>` 的规则自动找函数。例如 `partition_standard` 模块订阅 `boot_cold_init` 不写 handler，就自动找 `partition_standard_handle_boot_cold_init`。

### 1.2 `partition_standard` 订阅了什么

`hyp/core/partition_standard/partition.ev`：

```text
subscribe boot_runtime_first_init()

subscribe boot_cold_init()
	priority first

subscribe boot_cold_init
	handler partition_standard_boot_add_private_heap()
	// This must run after hyp_aspace_handle_boot_cold_init (priority 20)
	// and memdb_handle_boot_cold_init (priority 10)
	priority 9

subscribe boot_cold_init
	handler partition_standard_boot_create_root_partition()
	priority last

subscribe boot_hypervisor_start()
	priority 100
```

读法：`partition_standard` 在 `boot_cold_init` 事件上挂了**三个 handler**，优先级分别是 `first` / `9` / `last`。注释直接点明依赖：`add_private_heap` 必须在 `hyp_aspace`(20) 和 `memdb`(10) 之后，所以排 `9`。

> 注意：**同一个模块可以在同一个事件上挂多个 handler**，每个 handler 有自己的优先级。这是 Gunyah 事件系统的常见用法——一个模块把"建骨架 / 补差额 / 收尾"拆成三个独立 handler，按顺序插入到整条链里。

### 1.3 `memdb_bitmap` 订阅了什么

`hyp/mem/memdb_bitmap/memdb.ev`：

```text
subscribe boot_cold_init()
	// Must run after pagetable init and hyp_aspace initialisation.
	priority 10

subscribe partition_add_ram_range(owner, phys_base, size)
	unwinder(owner, phys_base, size)
```

`priority 10`，比 `partition` 的 `first` 晚、比 `add_private_heap(9)` 早。注释里"Must run after pagetable init and hyp_aspace initialisation"——意思是 memdb 在登记归属时会用到 `partition_image_virt_to_phys()` 这种"虚拟→物理"的换算，而换算依赖页表已经建好，所以必须排在 pgtable / hyp_aspace 之后。

### 1.4 什么是 `unwinder`（回滚 handler）

第二段里的 `unwinder(owner, phys_base, size)` 是个新概念，值得专门说一下。

`partition_add_ram_range` 是一条**事件**（不是函数），它自己也有一串订阅者。正常情况下这些订阅者按顺序跑，每个都做一点活：memdb 登记归属、allocator 加一段堆、list 插入一个节点……如果跑到第 3 个时失败了怎么办？已经跑过的前 2 个不能就这么留着——否则状态就半残了。

`unwinder` 就是"反向回滚函数"：事件链失败时，系统会**按相反顺序**调用每个已成功 handler 对应的 unwinder，把刚才做的事撤销。memdb 的 unwinder 干的事就是：把我刚才 `memdb_insert` 进去的那段归属删掉。

> 类比：unwinder 就是数据库事务的 ROLLBACK。每个 handler 是事务里的一条 SQL，挂了就回滚到事务开始前。

下面这张图把"正向执行 + 失败回滚"画出来，帮助理解 unwinder 的逆序回滚：

![unwinder 正向执行与反向回滚](图/第2课-unwinder.svg)

读法：上面是正常正向跑，每个 handler 干一点活；中间 handler3 失败；下面系统自动逆序调 handler2、handler1 的 unwinder 撤销。最终效果就像整条链从没跑过。

### 1.5 `thread_standard` / `idle` 订阅了什么

`hyp/core/thread_standard/thread.ev`：

```text
subscribe boot_runtime_warm_init
	priority last

subscribe object_init_thread(thread_create)

subscribe object_create_thread
	unwinder
	// Run first to ensure that thread kind is set
	priority first
```

注意：`thread_standard` **没有**订阅 `boot_cold_init`；它真正动手建 idle 线程是在 `boot_runtime_first_init`（更早，还在汇编里触发）。`idle` 模块才是那个早期 handler 的提供者（见第 4 节）。

> 关键认知：`boot_cold_init` 上的订阅者**不是全部模块**，只是"需要建全局数据结构"的那批。线程相关的早期工作在 `boot_runtime_first_init` 就做完了——因为切线程这件事不能等到 C 阶段，TPIDR 必须尽早合法。

## 2. 优先级总表：`boot_cold_init` 上的执行顺序

把本课涉及的 handler 按优先级排出来（数字越大越晚；`first`≈最早，`last`≈最晚）：

| 顺序 | 优先级 | handler | 模块 | 干的事 |
|------|--------|---------|------|--------|
| 1 | first | `partition_standard_handle_boot_cold_init` | partition | 建 hyp 分区：链表、allocator、把镜像内存划给自己 |
| 2 | 20 | `hyp_aspace_handle_boot_cold_init` | hyp_aspace | 建好 hyp 虚拟地址空间映射（本课不展开） |
| 3 | 10 | `memdb_bitmap_handle_boot_cold_init` | memdb | 把"镜像内存"和"bootmem"在 memdb 里登记归属 |
| 4 | 9 | `partition_standard_boot_add_private_heap` | partition | 把超过 2MiB 的私有堆补进 allocator |
| 5 | last | `partition_standard_boot_create_root_partition` | partition | 分配并激活 root partition，给它捐一块启动堆 |
| … | … | （其他模块：pgtable / gicv3 / irq / scheduler …） | … | … |

> `hyp_aspace`(priority 20) 和 `pgtable` 更早，本课先不展开，只要知道它们在 `partition(first)` 之后、`memdb(10)` 之前。

### 2.1 优先级数字的含义

- `first`：在所有数字优先级之前跑（相当于"最早"）。
- `last`：在所有数字优先级之后跑（相当于"最晚"）。
- 数字之间按数值排序：9 < 10 < 20，数字大的后跑。
- **同优先级**的 handler 顺序未定义，所以不要依赖"同优先级谁先"。

### 2.2 为什么是这个顺序——一句话口诀

记住一句口诀：**先有分区骨架 → 再建映射 → 再登记归属 → 再补私有堆 → 最后造 root partition**。

为什么不能反过来？
- 没有 `partition_hyp`（first）就没有 owner，memdb 不知道"登记给谁"。
- 没有 `hyp_aspace`（20）的映射，`partition_image_virt_to_phys()` 这种地址换算就用不了。
- 没有 memdb（10）登记，add_private_heap（9）补的堆就不知道该记在谁名下。
- 没有 allocator 喂饱，create_root_partition（last）就没法从 allocator 里分出 root partition 对象。

每一步都**依赖前面所有步**——这就是优先级链的内在逻辑。

下面这张依赖图把"谁依赖谁"画成箭头，比表格更直观：

![boot_cold_init 优先级依赖链](图/第2课-优先级依赖.svg)

读法：横向是时间（左早右晚），箭头表示"右边依赖左边"。每一步下方标注它**为什么必须排在那个位置**。如果反过来排，箭头就断了——后面那步拿不到它需要的东西。

## 3. 串讲：一页内存在启动期归谁管

跟着上面 5 个 handler，把"一页内存"的归属路径走一遍。这一节是本课的核心，建议对照源码读。

### 3.1 第 1 步：`partition_standard_handle_boot_cold_init`（priority first）

`hyp/core/partition_standard/src/init.c`：

```c
static partition_t  partition_hyp;     // 静态分配的 hyp 分区
static partition_t *partition_root;   // 稍后才建

void NOINLINE
partition_standard_handle_boot_cold_init(void)
{
	list_init(&partition_hyp.mapped_ranges);
	atomic_store_release(&partition_hyp.header.state, OBJECT_STATE_ACTIVE);

	partition_mapped_range_t *mr = bootmem_allocate(sizeof(*mr), alignof(*mr));
	...
	mr->virt = virt_start; mr->phys = phys_start;
	mr->size = (size_t)(hyp_heap_end - phys_start);
	list_insert_at_tail_release(&partition_hyp.mapped_ranges, &mr->list_node);

	allocator_init(&partition_hyp.allocator);
	...
	void_ptr_result_t ret = bootmem_allocate_remaining(&hyp_alloc_size);
	...
	trigger_allocator_add_ram_range_event(&partition_hyp, phys, ...);
}
```

逐段拆解：

1. **`partition_hyp` 是静态变量**（`static partition_t partition_hyp;`）。为什么不 `malloc`？因为此刻**还没有 allocator**——allocator 就是这个函数后半段才建的。静态变量在编译期就分配好 BSS，零成本可用。
2. **`list_init` + `atomic_store_release(... OBJECT_STATE_ACTIVE)`**：把 partition 的链表头和状态字段初始化好，标记为"已激活"。`atomic_store_release` 是带 release 屏障的写，保证后续读者能看到前面所有初始化。
3. **`bootmem_allocate(sizeof(*mr), ...)`**：从一个最原始的 bump 分配器（bootmem）里抠一小块内存放 `mapped_range` 节点。bootmem 是汇编阶段就准备好的"启动期临时分配器"，只会单调递增地切内存，不会回收。
4. **`mr->virt / phys / size`**：把 hypervisor 镜像那段内存（从 `image_phys_start` 到 `hyp_heap_end`）登记为"本分区映射过的一段"。注意这里登记的是**映射关系**（虚→物对应），**不是归属**——归属要等下一步 memdb 来记。
5. **`allocator_init(&partition_hyp.allocator)`**：建好 hyp 分区自己的 allocator 管理结构（空闲链表 / bitmap 之类）。
6. **`bootmem_allocate_remaining(&hyp_alloc_size)`**：把 bootmem 剩下的内存**一次性全过户**给 hyp 的 allocator。从这一刻起，bootmem 退役，allocator 接管。
7. **`trigger_allocator_add_ram_range_event(...)`**：又触发一个子事件，让 allocator 把这段内存加进自己的空闲池。

要点：
- `partition_hyp` 是**静态变量**，不经过 allocator，因为现在 allocator 还没建好。
- `bootmem` 是启动期最原始的 bump 分配器；`bootmem_allocate_remaining` 把剩下的内存**一次性过户**给 hyp 的 allocator。
- 这里只登记"映射关系"，**归属（谁拥有）**还没落到 memdb。

> 类比：这一步像盖房子前先搭脚手架。`partition_hyp` 是地基（静态），`bootmem` 是临时工棚，`allocator` 是正式仓库。盖完仓库就把工棚里的料全搬进仓库。

### 3.2 第 2 步：`memdb_bitmap_handle_boot_cold_init`（priority 10）

`hyp/mem/memdb_bitmap/src/memdb.c`：

```c
void
memdb_bitmap_handle_boot_cold_init(void)
{
	partition_t *hyp_partition = partition_get_private();
	spinlock_init(&memdb_lock);

	// 把 hypervisor 镜像这段物理内存标记为"归 hyp_partition 所有"
	error_t err = memdb_insert(hyp_partition,
		(paddr_t)&image_phys_start, (paddr_t)&image_phys_last,
		(uintptr_t)hyp_partition, MEMDB_TYPE_PARTITION);

	// 把 bootmem 那段从"partition 拥有"改成"allocator 拥有"
	void *bootmem_virt_base = bootmem_get_region(&bootmem_size);
	paddr_t bootmem_phys_base = partition_image_virt_to_phys(...);

	err = memdb_update(hyp_partition,
		bootmem_phys_base, bootmem_phys_base + (bootmem_size - 1U),
		(uintptr_t)&hyp_partition->allocator, MEMDB_TYPE_ALLOCATOR,
		(uintptr_t)hyp_partition, MEMDB_TYPE_PARTITION);
}
```

逐段拆解：

1. **`partition_get_private()`**：拿到上一步建好的 `partition_hyp`。这就是为什么这一步必须排在 `partition(first)` 之后——没有 first 那步，这里就拿到 NULL。
2. **`spinlock_init(&memdb_lock)`**：memdb 是全局共享的归属账本，多 CPU 会并发查询/修改，所以需要一把自旋锁保护。这里只是初始化锁，真正用锁是在 `memdb_update` 里 `spinlock_acquire(&memdb_lock)`。
3. **`memdb_insert(... image_phys_start .. image_phys_last .. MEMDB_TYPE_PARTITION)`**：把 hypervisor 镜像那段物理内存标记为"归 hyp_partition 所有"。`MEMDB_TYPE_PARTITION` 表示这段内存的 owner 是一个 partition 对象。
4. **`bootmem_get_region(&bootmem_size)`**：问 bootmem "你当初管的那段内存是哪一段？"。然后 `partition_image_virt_to_phys` 把虚地址换算成物理地址——这就是为什么 memdb 必须排在 hyp_aspace(20) 之后：换算依赖页表。
5. **`memdb_update(... MEMDB_TYPE_ALLOCATOR, ..., MEMDB_TYPE_PARTITION)`**：这是"改主"操作。参数含义是"把 bootmem_phys_base..bootmem_phys_base+size 这段，从 `MEMDB_TYPE_PARTITION`（partition 持有）改成 `MEMDB_TYPE_ALLOCATOR`（allocator 持有）"。因为上一步 partition 已经把 bootmem 剩余内存过户给 allocator 了，账本也得跟着改。

要点：
- `memdb` 是**全局物理内存归属数据库**：每一页物理内存都标着"归哪个 partition / allocator / …"。
- `memdb_insert` 是新增归属；`memdb_update` 是**改主**——把 bootmem 从"partition 持有"过户给"allocator 持有"。
- 这就是为什么 `memdb(10)` 必须在 `partition(first)` 之后：得先有 `partition_hyp` 这个 owner，才能登记归属。

> 类比：memdb 是地籍册（不动产登记簿）。partition 是房产证持有人，allocator 是物业。第一步 partition 买了房（first），第二步 memdb 才能在地籍册上写"这套房归 partition"。然后 partition 把房子委托给物业打理，memdb 就把登记改成"由 allocator 代管"。

### 3.3 第 3 步：`partition_standard_boot_add_private_heap`（priority 9）

`hyp/core/partition_standard/src/init.c`：

```c
void NOINLINE
partition_standard_boot_add_private_heap(void)
{
	// Only the first 2MiB of RW data was mapped in the assembly mmu_init.
	// The remainder is mapped by hyp_aspace_handle_boot_cold_init.
	if ((size_t)PLATFORM_HEAP_PRIVATE_SIZE > 0x200000U) {
		size_t remaining_size =
			(size_t)PLATFORM_HEAP_PRIVATE_SIZE - 0x200000U;
		paddr_t remaining_phys =
			(phys_last + 1U) -
			((size_t)PLATFORM_RW_DATA_SIZE - 0x200000U);

		error_t err = partition_add_heap(&partition_hyp, remaining_phys,
						 remaining_size);
		...
	}
}
```

逐段拆解：

1. **`PLATFORM_HEAP_PRIVATE_SIZE > 0x200000U`**：先判断"私有堆是不是超过 2MiB"。为什么是 2MiB？因为汇编阶段的 `mmu_init` 只用 2MiB 大页（AArch64 block mapping）映射了前 2MiB 的 RW data，剩下的没映射。
2. **`remaining_size = PLATFORM_HEAP_PRIVATE_SIZE - 0x200000U`**：算出"超过 2MiB 的那部分有多大"。
3. **`remaining_phys = (phys_last + 1U) - (PLATFORM_RW_DATA_SIZE - 0x200000U)`**：算出"超出的那部分从哪个物理地址开始"。这里在镜像的 RW data 区里倒着算。
4. **`partition_add_heap(&partition_hyp, remaining_phys, remaining_size)`**：把这段补进 hyp 分区的 allocator。`partition_add_heap` 内部会同时更新 memdb 归属和 allocator 空闲池——所以它必须在 memdb(10) 之后跑，否则 memdb 还没准备好接归属登记。

要点：这一步只是"补差额"——把汇编没映射的那部分私有堆补进 allocator。所以它优先级 `9`，必须在 `hyp_aspace(20)` 把映射建好、`memdb(10)` 把归属登记好之后才能跑。

> 类比：汇编只铺了前 2 米的地板，剩下的得等水电（hyp_aspace）和产权（memdb）都到位了再铺。这一步就是补铺剩下的地板。

### 3.4 第 4 步：`partition_standard_boot_create_root_partition`（priority last）

`hyp/core/partition_standard/src/init.c`：

```c
void NOINLINE
partition_standard_boot_create_root_partition(void)
{
	// 从 hyp 的 allocator 里分配出 root partition 对象
	partition_ptr_result_t part_ret = partition_allocate_partition(
		&partition_hyp, (partition_create_t){ 0 });
	...
	partition_root = (partition_t *)part_ret.r;

	partition_option_flags_set_privileged(&partition_root->options, true);
	object_activate_partition(partition_root);

	// 给 root partition 捐一块启动堆
	error_t err = partition_mem_donate(&partition_hyp, root_phys,
		root_heap_size, partition_root, from_heap);
	err = partition_map_and_add_heap(partition_root, root_phys, root_heap_size);
}
```

逐段拆解：

1. **`partition_allocate_partition(&partition_hyp, ...)`**：从 hyp 分区的 allocator 里分配出一个新的 `partition_t` 对象——这就是 root partition。注意是"从 allocator 分配"，所以必须排在 allocator 喂饱之后（即 last）。
2. **`partition_root = part_ret.r`**：把指针存到静态变量里，后面 `partition_get_root()` 就靠它返回。
3. **`partition_option_flags_set_privileged(..., true)`**：标记 root partition 为"特权"——它就是后面跑 RM / Root VM 的那个分区，需要特权。
4. **`object_activate_partition(partition_root)`**：激活这个 partition 对象（状态机转到 ACTIVE）。
5. **`partition_mem_donate(&partition_hyp, root_phys, root_heap_size, partition_root, from_heap)`**：把一块内存从 hyp 分区"捐"给 root 分区。`from_heap` 表示这块内存是从 hyp 的堆里分出来的（而不是从镜像尾部直接切的）。
6. **`partition_map_and_add_heap(partition_root, root_phys, root_heap_size)`**：在 root 分区里把捐来的内存映射好、加进 root 自己的 allocator 堆。

要点：
- root partition 是**从 hyp 的 allocator 里分配出来的对象**——这就是为什么它必须排在 `last`：前面所有步骤都得先把 allocator 喂饱。
- `partition_mem_donate` = 把内存从 hyp 过户给 root；这在后续 L3（内存与隔离）会细讲，本课只要知道"捐"= 改归属。
- 这一步之后，Root VM / RM 才有地方放自己的数据。

> 类比：hyp 分区是总公司，root partition 是子公司。总公司先得有金库（allocator 喂饱），才能拨一笔钱出来注册子公司（allocate partition），再给子公司拨一笔启动资金（donate heap）。子公司有了钱才能开张。

### 3.5 一页内存的归属路径（小结）

![一页内存：持有者 vs 归属账本](图/第2课-内存归属.svg)

一句话：**partition 是"持有者"，memdb 是"归属账本"，allocator 是"零钱罐"**。启动期就是把这三者按顺序搭起来，再把账本填上。

读法：从上往下是时间。注意 ① 那一步 memdb 账本还是空的——**持有者变了，账本还没动**；到 ② memdb 才把账本填上。这就是"持有者"和"归属账本"分离的体现：partition 先把东西拿在手里，memdb 稍后才在账本上补记一笔。

## 4. 旁路：idle 线程其实更早就建好了

`thread_standard` 没在 `boot_cold_init` 上干活，因为 idle 线程在更早的 `boot_runtime_first_init`（还在汇编里触发）就建好了。

`hyp/core/idle/src/idle.c`：

```c
void
idle_handle_boot_runtime_first_init(cpu_index_t boot_cpu_index)
{
	// 从 bootmem 里抠一块当 boot CPU 的 idle thread + TLS
	ret = bootmem_allocate(thread_size, thread_align);
	...
	boot_thread = (thread_t *)ret.r;
	memset_s(boot_thread, thread_size, 0, thread_size);

	trigger_object_init_thread_event(idle_params, hyp_partition);

	boot_thread->cpulocal_current_cpu = boot_cpu_index;

	// 必须是 boot_runtime_first_init 的最后一步
	thread_switch_boot_thread(boot_thread);
}
```

逐段拆解：

1. **`bootmem_allocate(thread_size, thread_align)`**：从 bootmem 直接抠一块内存当 idle 线程 + TLS（线程本地存储）。注意是 `bootmem_allocate`，不是 `partition_alloc`——因为此刻 partition/allocator 都还没建好（它们要等 `boot_cold_init` 才建）。
2. **`memset_s(...)`**：把整块清零。TLS 区域必须清零，否则线程一上来读到的就是脏数据。
3. **`trigger_object_init_thread_event(...)`**：触发"线程对象初始化"事件。这里只做最基本的初始化（设 thread kind、调度器阻塞状态等），完整的 `object_create_thread` 要等后面 allocator 能用了才补。
4. **`boot_thread->cpulocal_current_cpu = boot_cpu_index`**：把当前 CPU 的 index 写进线程的 cpulocal 字段。这是后面 `TRACE` / `LOG` 能用的前提——日志系统需要知道"现在是哪个 CPU 在说话"。
5. **`thread_switch_boot_thread(boot_thread)`**：切换到这个新线程。注释明确说"must be the last operation"——切过去之后，当前栈/寄存器上下文就换了，本函数不能再做任何事。

要点：
- idle 线程**没有走正常的 create 流程**，因为此时 partition/allocator 都还没建好，只能从 bootmem 直接抠。
- `thread_switch_boot_thread` 是这一步的**最后一句**——切过去之后，当前 CPU 才算有了一个"合法的当前线程"，后面所有 C 代码才能安全碰 TLS / CPU-local。
- 这正好呼应第 1 课的"为什么 `boot_runtime_first_init` 必须在汇编里触发"：因为切线程之前没有合法 TPIDR。

> 后续每个 CPU 的 idle 线程走的是正常流程 `idle_thread_create()` → `partition_allocate_thread()`，那时 allocator 已经能用了。见 `idle_thread_init()`。

### 4.1 idle 线程的"半成品"状态

注意一个细节：boot CPU 的 idle 线程在 `boot_runtime_first_init` 时只做了 `object_init_thread`（部分初始化），完整的 `object_create_thread`（补全调度器、栈等）要等到 `idle_thread_init()` 在 `boot_cold_init` 之后才补上。所以中间有一段窗口期，idle 线程是"半成品"——能跑，但不完整。

这就是为什么 `idle.c` 顶部注释写："we perform part of the boot with an incomplete idle thread structure"。

下面这张时间线图把 boot CPU 的 idle 线程从"抠内存"到"补全"再到"开跑"的整个过程画出来，帮助理解它为什么是"半成品"：

![idle 线程半成品窗口](图/第2课-idle时间线.svg)

读法：横向是时间。注意 `boot_runtime_first_init` 到 `boot_cold_init` 之间有一段"半成品"窗口——idle 线程已经能跑（TPIDR 合法），但完整初始化要等到 `idle_thread_init()` 在 `boot_cold_init` 之后才补。这就是为什么 idle 是"特例"：它必须早建（切线程要用），但又没法一次建完（allocator 还没有）。

### 4.2 idle 线程最终去哪儿

`boot_cold_init` 走完后，最后一句 `thread_boot_set_idle()` 把当前线程切到 idle 线程，进入 `idle_loop()`：

```c
static noreturn void
idle_loop(uintptr_t unused_params)
{
	preempt_disable();
	...
	do {
		scheduler_yield();
		// If yield returned, nothing is runnable
		while (!idle_yield()) {
			// Retry until an IRQ or other wakeup event occurs
		}
	} while (1);
}
```

idle 线程就是 hypervisor 的"待机模式"：没有 VCPU 可跑时，CPU 在这里转圈等中断唤醒。

### 5.1 怎么读这张图

- **从上往下**是时间顺序，上面的必须先发生。
- **缩进**表示同一个事件上的多个订阅者，按优先级从上到下排。
- **箭头**表示事件之间的先后触发关系（一个 `trigger_*` 跑完才到下一个）。

### 5.2 三个关键时间点

1. **`boot_runtime_first_init` 结束**：CPU 有了合法的当前线程（idle），可以安全用 TLS。
2. **`boot_cold_init` 结束**：partition / memdb / allocator / root partition 全部就位，内存管理框架搭好。
3. **`boot_cpu_cold_init` 结束**：CPU index 写进线程，`TRACE` / `LOG` 可用（这就是为什么 `boot.c` 里 `boot_cpu_cold_init` 之后才出现第一句 `TRACE_AND_LOG`）。

## 本课你要带走的三句话

1. **拼装方式**：`.ev` 里 `subscribe` + `priority`；`trigger_*` 按优先级广播；`unwinder` 负责失败回滚。
2. **启动期内存三件套**：`partition`（持有者）→ `memdb`（归属账本）→ `allocator`（零钱罐）；`boot_cold_init` 上四个 partition/memdb handler 就是把它们按顺序搭起来。
3. **idle 线程是特例**：在 `boot_runtime_first_init` 就从 bootmem 直接抠出来，不走正常 create 流程，因为那时 allocator 还没建好。
