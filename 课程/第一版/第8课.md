# 第 8 课 · L5 对外 API：Hypercall、CapID、跨 VM IPC

按学习地图：Guest 已经能跑、能收虚拟中断；今天换到 **Guest 视角**——它怎么向 hyp 要服务，以及跨 VM 通信的对象模型。

> 本课目标：能分清 `hvc #0` 和 `hvc #0x6000+`；能用三层模型讲清 Object / Capability / CapID；能口述 doorbell「同一对象、两份不同权利的 cap」。不要通读整份 API 文档。

---

## 0. 先对齐：Guest 永远拿不到 hyp 指针

第 4 课 `rootvm_init` 已经在做这件事：写进 env 的是 `cspace_capid` / `partition_capid` / `vcpu_capid`，不是 `cspace_t *`。本课把这条规则说完整。

文档（`docs/api/gunyah_api.md`，只读 ABI + CapID 段）：

> Capabilities are objects within a Capability Space (CSpace). These are not directly accessible to hypervisor clients (VMs). Instead, a VM uses Capability IDs (CapID) which index into a CSpace.

一句话：**Object 住在 hyp；Capability 住在 CSpace；Guest 口袋里只有 CapID。**

本课不扫完全文 API。够用的章节：AArch64 HVC ABI、CapID/Rights、Object Creation、Capability Management、Doorbell/Msgqueue。其余（virtio、SMMU、FF-A…）留给地图上的 L6，按兴趣选一条。

## 1. 两条 HVC 世界

![HVC 分流](图/第8课-HVC分流.svg)

| | `hvc #0` | `hvc #0x6000` … `#0x61ff` |
|--|----------|---------------------------|
| 规范 | ARM SMCCC | Gunyah 自己的 hypercall |
| Call-ID 在哪 | `x0` 的 Function ID | **指令 immediate** |
| 谁处理 | `smccc_handle_vcpu_trap_hvc64` | `vectors.S` 里的 `hypercall_table` |
| 例子 | PSCI `CPU_ON`（第 7 课） | `doorbell_send` = `hvc #0x6012` |

`tools/hypercalls/hypercall.py` 写死：`abis['aarch64'] = abi_aarch64(0x6000)`。实际 Call-ID = `0x6000 + call_num`。参数/返回走 AAPCS64 的 `x0–x7`；`x0=0` 为 OK，`x0=-1` 为未实现。未用的结果寄存器不保证保留。

向量入口（`hyp/vm/vcpu/armv8-64/src/vectors.S`）：

```asm
.macro hypercall_decode_native ...
	mrs	x18, ESR_EL2
	// 取出 ISS（imm16）
	ubfx	x18, x18, 0, 16
	sub	x18, x18, HYPERCALL_BASE
	cmp	x18, HYPERCALL_NUM
	b	hypercall_64_entry
```

在范围内：按下标跳 `hypercall_table`，进生成的 C wrapper：`thread_entry_from_user` → `hypercall_<name>(...)` → `thread_exit_to_user`。不在范围内：落到普通 sync 异常；其中 `imm16==0` 交给 SMCCC。

不要把两类 HVC 混进同一张表。Guest Linux 的 PSCI 走 `#0`；Gunyah 的「创建对象 / 按铃 / map 内存」走 `0x6000+`。

## 2. 三层模型

![Object / Cap / CapID](图/第8课-CapID.svg)

| 层 | 在哪 | Guest 可见 |
|----|------|------------|
| **Object**（partition / thread / doorbell / msgqueue / memextent…） | hyp 堆 | 否 |
| **Capability**（slot：对象指针 + rights + state） | 某 CSpace 的表 | 否 |
| **CapID** | 寄存器大小的不透明整数 | **是**（唯一句柄） |

同一对象可以有多份 cap，权利可以不同：A 只有 Send，B 只有 Receive。拷贝用 `cspace_copy_cap_from`（HVC `0x6023`），拷贝出来的 **不是** master cap，且 rights 被 mask 收紧。

CapID **只在所属 CSpace 内有意义**。两个 VM 上相同的数字不是同一份 capability；也不要当成 hyp 指针或全局对象 ID。

创建套路（生成代码，`partition_standard` 模板）：

```c
hypercall_partition_create_*(cap_id_t src_partition_cap, cap_id_t cspace_cap)
{
	cspace_t *cspace = cspace_get_self();
	// lookup partition（要 OBJECT_CREATE 权利）
	// lookup dest cspace（要 CAP_CREATE 权利）
	obj = partition_allocate_*(...);
	capid = cspace_create_master_cap(dest_cspace, obj, OBJECT_TYPE_*);
	ret.new_cap = capid;   // 还给 Guest 的只有这个整数
}
```

教学顺序：partition 造对象 → 在 dest CSpace 建 master CapID → configure → activate →（可选）降权拷贝到另一 VM → `cspace_attach_thread` 让某条 VCPU 用那个 CSpace。第 4 课 RootVM 就是这条链的启动版。

## 3. 两级 CSpace：怎么从号码牌找到对象

实现：`hyp/core/cspace_twolevel/`。CapID 不是裸的表下标：

```c
// VM visible cap-IDs are randomized.
static cap_id_t
cspace_encode_cap_id(const cspace_t *cspace, cap_value_t val)
{
	uint64_t v = (uint64_t)cap_value_raw(val);
	return (cap_id_t)((v * cspace->id_mult) ^ cspace->id_rand_base);
}
```

内部才是 16 位：`upper_index` 8 bit + `lower_index` 8 bit → `cspace->tables[upper]->cap_slots[lower]`。每个 cspace 开机时抽自己的 `id_mult` / `id_rand_base`，所以 CapID 跨启动、跨 cspace 都不可猜。

![两级查找](图/第8课-两级CSpace.svg)

查找：

```c
object_ptr_result_t
cspace_lookup_object(cspace_t *cspace, cap_id_t cap_id, object_type_t type,
		     cap_rights_t rights, bool active_only)
{
	cspace_lookup_cap_slot(cspace, cap_id, &cap);
	cspace_check_cap_data(cap_data, type, rights);
	return object_ptr_result_ok(cap_data.object);
}
```

当前线程的 CSpace：

```c
cspace_t *
cspace_get_self(void)
{
	return thread_get_self()->cspace_cspace;
}
```

几乎每个 hypercall 开头都是：`cspace_get_self()` + `cspace_lookup_<obj>(..., CAP_RIGHTS_...)`。指针只在这一次调用内存活，用完 `object_put_*`。Guest 侧没有任何「缓存对象地址」的合法做法。

第 4 课 `cspace_attach_thread(root_cspace, root_thread)` 的意义现在清楚了：RootVM 的 VCPU 做 HVC 时，查的就是 root cspace 那张表。

## 4. Doorbell：跨 VM 按铃

两者都是 **hyp 里的一份共享对象**；VM A / B 各持指向它的、权利不同的 CapID。不共享 Guest 内存，不传指针。

![doorbell 跨 VM](图/第8课-doorbell.svg)

```c
// hyp/ipc/doorbell/src/hypercalls.c
hypercall_doorbell_send_result_t
hypercall_doorbell_send(cap_id_t doorbell_cap, uint64_t new_flags)
{
	cspace_t *cspace = cspace_get_self();
	doorbell_ptr_result_t p = cspace_lookup_doorbell(
		cspace, doorbell_cap, CAP_RIGHTS_DOORBELL_SEND);
	res = doorbell_send(doorbell, (doorbell_flags_t)new_flags);
	object_put_doorbell(doorbell);
}
```

内核语义（`hyp/ipc/doorbell/src/doorbell.c`）：

```c
doorbell_send(doorbell_t *doorbell, doorbell_flags_t new_flags)
{
	flags |= new_flags;
	bool edge_only =
		(flags & atomic_load_relaxed(&doorbell->enable_mask)) == 0U;
	atomic_store_relaxed(&doorbell->flags, flags);
	(void)virq_assert(&doorbell->source, edge_only);
}
```

`virq_assert` 就是第 7 课的注入路径。故事可以缩成：

1. Root/VM0 创建 doorbell 对象，得到 master cap。
2. 给 VM-A 拷贝 **Send** cap，给 VM-B 拷贝 **Receive + Bind** cap。
3. B 把自己的 VIC 绑上去（`doorbell_bind_virq`，HVC `0x6010`）。
4. A 调 `doorbell_send`（`0x6012`）→ hyp 改 flags → `virq_assert` → B 的 vCPU 收到 vIRQ。
5. B 再 `doorbell_receive` 读/清 flags。

Rights：Send `0x1` / Receive `0x2` / Bind `0x4`。没有 Send 权利的 CapID 在 lookup 就会失败，A 没法冒充 B 去收铃。

**Msgqueue** 同构，只是多一个有界环形缓冲和一对 VIRQ（send 侧空位、recv 侧有数据）。数据经 `user_ptr_t`（Guest VA）由 hyp 拷进对象缓冲。Call-ID：send `0x601B`，receive `0x601C`。本课记住「对象在 hyp、两边各持 cap」即可，不必跟缓冲区实现。

## 5. 和前几课怎么接上

- 第 4 课 RootVM env 里的 CapID，就是本课 Guest 后续 hypercall 要传的号码牌。
- 第 6 课 `hypercall_addrspace_map(addrspace_cap, memextent_cap, ipa, …)`：两个参数都是 CapID；hyp 内部 lookup 成指针再 `memextent_map`。
- 第 7 课 doorbell 最终落到 `virq_assert` → ICH_LR。IPC 不是另一套中断，是「对 hyp 对象操作 → 复用 VGIC」。
- 第 5 课：做 hypercall 的是 **当前这条 VCPU 线程**；`cspace_get_self()` 读的是它 attach 的那张表。

## 6. L6 怎么继续（选一条，不要全铺）

地图上的 L6 是平台与设备虚拟化，主题多。学完 L5 之后按兴趣跟 **一条** 端到端即可，例如：

- VirtIO：`hyp/vm/virtio*` + 后端
- SMMU：`hyp/platform/smmuv3/`（DMA 隔离，和 L3 的 Stage-2 成对）
- FF-A：`hyp/platform/ffa/`
- 代码生成：`tools/codegen/`、`tools/hypercalls/`、`tools/events/`（你已经用事件系统很久了）

完成标准和地图一致：能独立跟一条路径（virtio 或内存捐赠），而不是把 `hyp/vm/` 扫一遍。

## 本课你要带走的三句话

1. **Gunyah hypercall 的 Call-ID 在 `hvc` 的 immediate 里**（`0x6000–0x61ff`），和 SMCCC 的 `hvc #0` / `x0` 不是同一套。
2. **Guest 只拿 CapID**：lookup 发生在 EL2，指针用完即 `object_put`；CapID 经随机编码，且只在本 CSpace 有效。
3. **跨 VM IPC = 同一 hyp 对象上的多份 cap**：doorbell send 最终 `virq_assert`，复用第 7 课的注入路径。
