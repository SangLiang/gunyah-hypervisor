## 1. 一张总图（先建立直觉）

```text
        CPU 侧                              设备侧
   ┌─────────────┐                    ┌─────────────┐
   │  程序 VA    │                    │ 描述符里的   │
   │      ↓      │                    │   IOVA      │
   │    MMU      │                    │      ↓      │
   │  (页表翻译)  │                    │  IOMMU/SMMU │
   │      ↓      │                    │  (页表翻译)  │
   │     PA      │                    │      ↓      │
   └─────────────┘                    │     PA      │
                                      └─────────────┘
         ↑                                   ↑
    CPU load/store                      设备自己 DMA
```

**核心对应：**

| | CPU | 设备 |
|--|--|--|
| 地址 | 虚拟地址 VA | IOVA |
| 翻译 / 门卫 | MMU | IOMMU（ARM 上常叫 **SMMU**） |
| 防的是啥 | 进程乱访别人内存 | 设备乱 DMA 到不该碰的内存 |

一句话：**IOMMU ≈ 设备端的 MMU。**

## 2. DMA 是什么

**DMA（Direct Memory Access，直接内存访问）**：外设自己读写内存，不经过 CPU 一条条搬数据。

- 没有 DMA：CPU 当搬运工，从设备寄存器反复读字节再写入内存。
- 有 DMA：CPU 只告诉设备「从哪搬到哪、搬多少」，设备自己完成，搬完再中断通知。

virtio-blk / virtio-net 等场景里，guest 在内存里摆好 virtqueue 描述符（buffer 地址与长度），backend 或真设备按这些地址去碰 guest 内存——概念上就是 DMA 路径上的「按地址访问内存」。

**记住：**

| 概念 | 含义 |
|--|--|
| CPU 访问内存 | 程序里的 load/store |
| DMA | **设备**按地址访问内存 |
| IOMMU | 专门给 DMA 用的地址翻译 + 权限检查 |

**DMA = 谁来搬；IOMMU = 搬的时候地址怎么走、允不允许走。**

---

## 3. IOMMU 是什么（纠正常见误解）

### 3.1 它做什么

IOMMU **不负责搬数据**，也不负责「找一块空闲内存」。  
操作系统先分配真内存；若启用 IOMMU，再建立映射，把 **IOVA** 交给设备。

设备发起访问时带上 IOVA → IOMMU **翻译成真实物理地址并检查权限** → 合法才放行。

### 3.2 设备眼里的「指针」

1. OS 分配物理页，建立 `IOVA → PA`（虚拟化里常是 `IOVA → GPA`，再叠一层）。
2. 驱动把 **IOVA** 填进设备描述符（你看到的「指针」）。
3. 设备按这个地址发总线事务。
4. IOMMU 在旁翻译/安检；设备通常无感。

### 3.3 页表：和 CPU 一样可以有 Stage-1 / Stage-2

虚拟化 + 设备直通时，SMMUv3 常常两级翻译，和 CPU 很像：

| | CPU MMU | IOMMU / SMMU |
|--|--|--|
| Stage-1 | VA → IPA（guest 页表） | IOVA → IPA/GPA（设备 IOMMU 页表） |
| Stage-2 | IPA → PA（hypervisor 页表） | IPA → PA（通常对齐该 VM 的 CPU stage-2） |

裸机或简单配置可能只有一级；嵌套虚拟化 / 直通进 guest 时，两级是常态。

### 3.4 谁来「实现」IOMMU

要分层看：

| 层 | 职责 |
|--|--|
| **硬件（SMMU 芯片）** | 真正做翻译与拦截 |
| **裸机 / Host 内核** | 驱动与建表（Linux：`iommu` 子系统 + `arm-smmu-v3` 等），暴露 DMA API |
| **虚拟化** | Guest 跑 `virtio-iommu`；**EL2/hypervisor** 仿真该设备并把请求落到真 SMMU |

结论：软硬件协同——芯片提供能力，软件编排建表与接口。虚拟化里软件再拆成 **guest 内核 + hypervisor** 两段。

## 4. 设备直通（Passthrough）

**方向：host 上的真设备 → 交给某个 guest 专用**（不是 guest 设备被 host 拿走）。

| 形态 | 含义 |
|--|--|
| 全模拟 / 纯 virtio | guest 见虚拟设备，backend 在 EL2 或 crosvm 软件实现 |
| **设备直通** | guest 直接驱动真硬件，性能好；DMA 隔离几乎总要靠 IOMMU |
| 中间方案 | vhost、SR-IOV VF 等 |

直通时真设备会自己发 DMA，必须用 IOMMU 把访问关进「属于该 guest 的页面」。若还要让 guest 按自己的 IOVA 模型编程，就再叠 **virtio-iommu**。

## 5. Virtio：协议

### 5.1 正确定义

- **virtio** = guest 与 hypervisor 之间的 **标准虚拟设备契约**  
  （设备外观、virtqueue、feature、配置空间、请求/响应格式）
- **backend** = 契约背后真正干活的实现

Guest 驱动只认协议，不关心对面是文件、tap，还是一颗 SMMU。

### 5.2 Backend 可以怎么干

| Backend 形态 | 例子 | 是否落到「同名真硬件」 |
|--|--|--|
| 纯软件 | virtio-blk 读写镜像；virtio-console → pty | 否 |
| 借 host 能力 | virtio-net → tap；vhost | 间接用 host，不是原样交同一块卡 |
| 落到真硬件控制面 | **virtio-iommu → 真 SMMU** | 是 |
| 与直通并列 | PCI 直通 GPU/网卡 | guest **常常不走 virtio**，直接驱动真设备 |

从 virtio-iommu 悟到「分层 + 接口」是对的；把整个 virtio 说成「转发到真硬件」会和 console/blk 的纯软件 backend 对不上。

### 5.3 一句话

**virtio 定任务格式；backend 定怎么完成（软件或硬件）。**

## 6. MMIO 是什么（别和 IOMMU 混）

**MMIO（Memory-Mapped I/O）**：把设备的 **控制寄存器** 映射到 CPU 可用普通 load/store 访问的一段地址。CPU 读写这些地址 = 在操作设备，不是在访问普通 RAM。

| | MMIO | DMA / IOMMU |
|--|--|--|
| 谁发起 | **CPU** | **设备** |
| 目的 | 配置、踢队列、查状态 | 搬大批数据 |
| 典型内容 | 寄存器窗口 | 大块 buffer |

virtio-mmio：guest 通过 MMIO 寄存器配置队列、写 kick；真正的数据描述符在普通内存的 virtqueue 里。

**MMIO = CPU → 设备；IOMMU = 设备 → 内存时的翻译门卫。**

## 7. 专题：virtio-iommu 调用链（讨论起点）

```text
guest Linux 标准驱动 (virtio-iommu, /dev/viommu)
    ↓ virtqueue 请求 (ATTACH / MAP / UNMAP / PROBE / INVALIDATE)
EL2 virtio_iommu (设备仿真 + 请求处理；常见：大锁 + smmuv3_sync)
    ↓ smmuv3 平台驱动 (如 hyp/platform/smmuv3)
物理 SMMUv3 (STE / CD 编程、TLB invalidate)
    ↓ 硬件翻译
直通设备的 DMA → guest 物理内存
```

### 7.1 三个地址

| 名字 | 谁眼里 | 含义 |
|--|--|--|
| IOVA | 设备 / guest DMA API | 描述符里的 DMA 地址 |
| GPA / IPA | guest | guest 物理 / 中间物理地址 |
| PA | 真机 | DRAM 真实物理地址 |

硬件路径：**设备发 IOVA → SMMU Stage-1 → GPA → Stage-2 → PA。**

### 7.2 各请求含义（控制面）

| 请求 | 作用 |
|--|--|
| PROBE | 查询 IOMMU 能力（页大小、地址宽度等） |
| ATTACH | 把 endpoint（常对应 PCI RID / StreamID）绑到 domain |
| MAP | 建立 IOVA → GPA（带权限） |
| UNMAP | 拆除映射 |
| INVALIDATE | 作废旧翻译缓存；嵌套场景下常触发 TLB/config 失效 |

### 7.3 EL2 在做什么

1. 仿真合规的 virtio-iommu 设备（队列、feature、config）。
2. 解析 guest virtqueue 请求。
3. 维护软件状态（endpoint ↔ domain、映射表）。
4. 调用平台 `smmuv3`，把 Stage-1 视图写入真硬件（STE/CD），再 invalidate + **sync**。

**大锁 + sync** 的原因：多 vCPU 并发 MAP/UNMAP；改表与 TLB 失效必须有序，避免和飞行中的 DMA 打架。

### 7.4 控制面 vs 数据面

```text
[配置期 / 控制面]
guest ATTACH/MAP → virtqueue → EL2 virtio_iommu → 写 STE/CD → sync → 返回

[运行期 / 数据面]
直通设备 DMA(IOVA) → 物理 SMMUv3（S1+S2）→ guest 内存
（EL2 不介入每一次 DMA）
```

与纯 virtio-blk 对比：blk 的数据路径上 backend 按描述符读 guest 内存；本链是 **真设备发 DMA**，EL2 只出现在 IOMMU **控制路径**。

### 7.5 和本仓库的对照（备忘）

- 设计稿提到 Gunyah 将 `virtio_input` / `virtio_iommu` 作为 **EL2 内简单 backend**；blk/net/gpu 的 EL2 backend 在 OSS 中通常没有完整实现。
- 平台侧已有 `hyp/platform/smmuv3`（STE/CD、`attach_stream`，可见嵌套配置如 `S1TRANSLATE_S2TRANSLATE`）。
- xhyper EL2 virtio 设计主线（console/blk）**不必然立刻依赖** virtio-iommu；直通 + guest 可编程 IOVA 时才强相关。

## 8. 容易混淆的概念速查

| 说法 | 对不对 | 更正 |
|--|--|--|
| IOMMU 让 CPU 不用搬数据 | 偏 | 那是 **DMA** |
| IOMMU 负责找空闲内存 | 错 | OS 分配；IOMMU 只翻译和检查 |
| IOMMU 让设备去读虚拟地址 | 措辞易混 | 设备一直用 IOVA；翻译在 IOMMU 内完成 |
| 直通 = guest 设备给 host | 反了 | host 真设备给 guest |
| virtio = 转发到真硬件 | 过窄 | virtio 是协议；backend 可选软件或硬件 |
| MMIO = 设备 DMA 用的地址映射 | 偏 | MMIO 是 CPU 访问设备寄存器的窗口 |

---

## 9. 复习口诀（六句）

1. **DMA**：设备自己搬内存。  
2. **IOMMU ≈ 设备端 MMU**：IOVA → PA，并做权限检查。  
3. **MMU / IOMMU 都可以有 Stage-1、Stage-2 页表。**  
4. **直通**：真设备进 guest；DMA 隔离靠 IOMMU。  
5. **virtio**：标准协议；**backend**：软件或硬件实现。  
6. **MMIO**：CPU 用「访存」方式拧设备寄存器；与 IOMMU 方向相反。
